# Безопасность CineDairy

## Реализовано

- Сессии Django в БД: HttpOnly/Secure/SameSite=Lax; production cookie с префиксом `__Host-`. HTTPS, CSRF, проверка Origin, отсутствие CORS-разрешений для посторонних сайтов. Срок сессии — до 7 суток, бездействие — до суток. Повторный вход обновляет идентификатор сессии.
- Вход по email: криптографически случайный восьмизначный код на 10 минут; HMAC с серверным секретом, одноразовое использование, максимум 5 проверок конкретного кода. Лимиты отправки: 5/час на адрес и 20/час на IP; проверки: 10/10 минут на адрес и 30/10 минут на IP. Счётчики в БД с блокировками, общий ответ для новых и существующих адресов. Повторная отправка аннулирует старый код. Паролей пользователя нет.
- Яндекс OAuth Authorization Code + PKCE S256, state, срок попытки 10 минут, фиксированный callback, проверка client_id. Токены провайдера не сохраняются. Идентичность определяется по provider+subject, не по email.
- Привязка нового способа входа требует недавнего подтверждения существующим способом и проверки нового. Email-код привязан к пользователю и сессии. Автоматического объединения аккаунтов нет.
- Приватность по умолчанию. API получает владельца из проверенной сессии. Дополнительный заголовок аккаунта обнаруживает смену cookie между вкладками, но сам по себе не предоставляет доступа. Публичных коллекций и общедоступных экспортов нет.
- Фильмы, просмотры, цитаты, подборки, состав подборок и фильтры — отдельные таблицы. Локальные ID принадлежат своему архиву. Метаданные отдельных записей хранятся в проверяемых JSON-полях. Сервер никогда не принимает owner_id из архива.
- Атомарная запись архива с проверкой версии и блокировкой PostgreSQL. Конфликт возвращает 409, не перезаписывая текущую версию. GET тоже берёт блокировку для согласованного снимка. Повторный гостевой импорт распознаётся по хешу содержимого. Цитаты отображаются как текст; данные проходят allowlist-проверку, ограничения длины, размера, дат и связей.
- В аккаунте localStorage не используется для личного архива или токенов. Несохранённая версия остаётся только в памяти вкладки. После выхода — очистка памяти и перезагрузка. Выход в другой вкладке обнаруживается через BroadcastChannel и проверку сессии; на другом устройстве — при следующем запросе/периодической проверке. При возврате из back-forward cache выполняется перезагрузка. Гостевые данные удаляются отдельным явным действием.
- CSP запрещает сторонние скрипты, inline-скрипты, встраивание во фреймы и произвольные соединения. Inline-стили оставлены для существующих динамических шкал. Постеры разрешены по HTTPS, с `Referrer-Policy: no-referrer`; сторонний сервер изображения всё ещё видит IP посетителя.
- Ключ Kinopoisk только на сервере при серверном размещении; фиксированный адрес upstream, таймаут и ограничение размера ответа. Произвольные URL сервер не загружает.
- В Compose нет опубликованных портов PostgreSQL или Django. Caddy — единственная публичная точка. Приложение работает непривилегированным пользователем, с read-only filesystem и без Linux capabilities. Runtime-роль БД отделена от владельца/мигратора/backup-роли.
- Логи приложения содержат только тип события и внутренний ID пользователя; тела, почта, OTP, provider tokens и строки поиска не логируются. HTTP access logging отключён, чтобы не сохранять OAuth code. Настройки внешнего reverse proxy/SMTP/хостинга проверяет оператор.
- Скрипт шифрует pg_dump публичным age-ключом, обрабатывает ошибки конвейера и публикует файл только после успеха. Приватный ключ хранится отдельно. Таймер подготовлен, но должен быть установлен оператором. Проверка восстановления — отдельный тест.
- Аккаунт удаляется после подтверждения входа за последние 10 минут; связанные данные удаляются каскадно. Резервные копии могут содержать прежние данные до истечения 30-дневного срока хранения. При восстановлении старой копии оператор должен повторно применить удаления из отдельного журнала запросов на удаление.

## Что не следует обещать пользователям

Это не сквозное шифрование. Приложение и привилегированный оператор могут прочитать архив. Защита от компрометации хостинга, ОС или почты пользователя не гарантируется. Шифрование рабочего диска/снимков, размещение в РФ, независимая копия и мониторинг требуют настройки выбранного провайдера; код приложения их сам не включает. Трафик app↔db внутри изолированного bridge одного VPS в базовом Compose не шифруется. Для внешнего PostgreSQL обязателен TLS verify-full с доверенным CA.

Веб-админка намеренно не опубликована. Администрирование выполняется оператором через защищённый доступ к серверу. MFA для кабинета хостинга и административного SSH/VPN настраивается у провайдера/оператора, а не в этом приложении. При добавлении веб-админки требуется отдельная MFA-интеграция до её публикации.

Без настроенного SMTP/Яндекс вход отключён в интерфейсе. Тестовые ответы SMTP/OAuth не подтверждают реальную доставку и регистрацию callback. Установленный в production `FILM_DEV=1` или `FILM_TEST=1` отключит часть защит; эти переменные не должны задаваться в рабочей среде.

## До открытия регистрации

1. Заполнить серверные секреты, настроить российские площадки основного сервера, SMTP и резервных копий. Подготовить описание обработки данных, сроков хранения и контакта владельца; конкретные юридические обязанности проверить отдельно.
2. Включить HTTPS; проверить реальные SMTP и Яндекс ID. Не использовать старый ключ Kinopoisk, ранее попавший в Git: отозвать его и выдать новый.
3. Проверить firewall, шифрование диска/снимков у провайдера, MFA администратора и доступ к `.env`.
4. Включить таймер backup, независимое копирование ciphertext и оповещение о сбое/отсутствии новой копии. Провести пробное восстановление на отдельной БД.
5. Запустить проверки из CI на используемом PostgreSQL и `manage.py check --deploy`. Не считать систему проверенной только по тестам SQLite.

## Эксплуатация и инциденты

- Регулярно обновлять поддерживаемые версии Django, PostgreSQL, контейнеров и ОС, проверять зависимости. Закреплённые Python-версии обновлять отдельным проверенным изменением.
- Каждый день запускать `manage.py prune_auth`: удаляет истёкшие коды, rate buckets и сессии. Проверять успешность backup и копирования за пределы сервера. Не публиковать резервные копии через веб-каталог.
- При утечке ключа — отозвать у провайдера, заменить серверную конфигурацию, пересоздать контейнеры. Изменение DJANGO_SECRET_KEY инвалидирует старые сессии и проверочные значения кодов. Не переносить скомпрометированный ключ в SECRET_KEY_FALLBACKS.
- При подозрении на утечку архива — ограничить доступ, сохранить технические свидетельства с минимизацией персональных данных, установить затронутый объём, выполнить процедуру уведомлений, применимую к владельцу сервиса.
- Отдельно хранить журнал исполненных удалений аккаунтов, чтобы восстановление старого backup не возвращало удалённые аккаунты в работу. В этой версии автоматической синхронизации такого журнала с off-server storage нет.

Не публикуйте реальные архивы и секреты в GitHub Issues. Сообщайте о проблеме владельцу приватно, используя искусственные примеры.
