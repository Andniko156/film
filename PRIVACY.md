# CineDairy: персональные данные и подготовка к публикации

Область: cinedairy.ru, аккаунты Django, Android WebView и сервер синхронизации. Проверка относится к коду и поставляемой конфигурации. Состояние рабочего VPS, договоры с провайдерами и сведения в реестре оператора требуют отдельного подтверждения.

## Что добавлено

- `/privacy.html` — публичная политика. `/consent.html` — отдельный текст согласия. Ссылки доступны на сайте и в разделе «Мой аккаунт» на Android. В приложении документы открываются в браузере; для просмотра нужна связь с сервером.
- На регистрации, входе по коду, привязке email и старте Яндекс ID показывается отдельный, изначально пустой чекбокс. Вход с существующим паролем и гостевой режим остаются доступны без повторного согласия.
- Сервер проверяет редакцию текста до отправки письма или перехода в Яндекс. Подтверждение кода связывает согласие с той же сессией и проверенным аккаунтом. Версия, точный текст, время и сценарий записываются в БД. Старые аккаунты не получают фиктивных записей о согласии.
- Отзыв доступен по контакту в документах. Действующее удаление аккаунта удаляет рабочий архив, связанное согласие и запись с кодом для подтверждённой почты. Уже выгруженные файлы и копии на других устройствах требуют отдельной очистки.

## Что подтвердить владельцу до включения

| Вопрос | Действие оператора |
| --- | --- |
| Оператор и обращения | Подтвердить ФИО или наименование, почтовый адрес и email для запросов. Организовать проверку личности, рассмотрение запросов, отзыв и уничтожение данных. |
| Инфраструктура | Подтвердить размещение рабочей базы, резервных копий и журналов. Для сбора данных граждан РФ проверить локализацию по ч. 5 ст. 18 152-ФЗ. Проверить также доступ из-за рубежа, отправку через SMTP, внешние изображения и запросы к API. При наличии трансграничной передачи отдельно проверить ст. 12 и необходимость уведомления. |
| Провайдеры | Сверить фактических поставщиков хостинга и SMTP, роли при обработке и договорные условия. Проверить состав полей Яндекс ID и правила Kinopoisk API Unofficial, включая использование постеров. Описать реальные передачи, включая страны, если применимо. |
| Уведомление | Проверить подачу уведомления об обработке или актуальность сведений в реестре Роскомнадзора по ст. 22. Для работающего сервиса проверить это без ожидания нового релиза. |
| Сроки и удаление | Настроить ежедневный `prune_auth`, ограничить сроки хранения журналов и копий у всех провайдеров. Выбрать срок, при котором выполняются обязанности по ст. 21. Применять удаления повторно после восстановления БД. Отдельно урегулировать сохранённые для восстановления копии объединённых аккаунтов: в текущей реализации источник становится неактивным, а его архив остаётся в БД. |
| Документы и меры | Утвердить тексты, основания и сроки для каждой цели, включая запросы поддержки, старые аккаунты, технические данные и обращение с ошибочно введёнными чужими данными. Проверить меры защиты, локальные документы и порядок уведомления об инцидентах. Отдельно проверить условия использования контента и правила выбранного магазина приложений перед публикацией. |

Основа: [152-ФЗ, статьи 6, 9, 12, 18, 18.1, 19, 21 и 22](https://mintrud.gov.ru/docs/laws/130), [разъяснение прокуратуры об отдельном согласии](https://epp.genproc.gov.ru/ru/proc_38/activity/legal-education/explain/otherwise/e5978821/), [портал персональных данных Роскомнадзора](https://pd.rkn.gov.ru/).

## Включение на VPS

До заполнения реквизитов документы показываются как проекты, а сервер оставляет прежний порядок входа. `PRIVACY_ENABLED=1` включает проверку согласия. Проверьте реальное содержание и укажите в `.env`:

- `PRIVACY_OPERATOR`, `PRIVACY_ADDRESS`, `PRIVACY_EMAIL` — данные оператора и контакт;
- `PRIVACY_HOSTING`, `PRIVACY_MAIL_PROVIDER` — подтверждённые сведения о поставщиках и размещении;
- `PRIVACY_BACKUP_DAYS`, `PRIVACY_AUDIT_DAYS` — реальные сроки. Эти переменные публикуют сроки, а очистку выполняют настроенные отдельно задания и политика хранения.

Установите обновлённый APK пользователям перед включением обязательной проверки. Android 0.2.1 и более ранние сборки не передают редакцию согласия: в них новые запросы кода и привязка email после включения будут отклонены. Пароль и действующие сессии продолжают работать. Коды, отправленные до включения проверки, нужно запросить повторно.

При развёртывании новой версии сначала примените миграцию, затем запустите обновлённый сервер. Пример для существующей установки Docker Compose:

```sh
docker compose config --quiet
docker compose build app migrate
docker compose --profile tools run --rm migrate
docker compose up -d app
```

Проверьте тексты по обоим адресам, отправку кода только после отдельной отметки, вход по паролю, запись согласия и отзыв на тестовом аккаунте. При изменении текста версия меняется автоматически. Ранее полученное согласие сохраняется с исходным текстом. Если изменение затрагивает основания или цели обработки, порядок получения согласия от действующих пользователей определяет оператор перед применением новых условий.
