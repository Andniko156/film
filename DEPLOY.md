# Развёртывание аккаунтов на российском VPS

Требуется Linux VPS с Docker Engine и Compose v2, домен и доступ к SMTP с TLS. Выберите размещение в РФ у своего провайдера. Для начала оцените VPS с 2 vCPU и 2–4 ГБ RAM; достаточность зависит от размера архивов и нагрузки. Это ориентир, не гарантия производительности.

Серверная версия не работает на обычном статическом хостинге. Без Django остаётся гостевой режим. Все исходники для пяти файлов интерфейса остаются в корне.

## 1. Подготовка

Склонируйте репозиторий в `/opt/film`, настройте A-запись домена на VPS и откройте для посетителей только 80/443. Административный SSH ограничьте ключами и доверенными адресами/VPN, включите MFA в кабинете хостинга. Не открывайте 5432 и 8000.

```sh
cd /opt/film
cp .env.example .env
chmod 600 .env
```

Заполните `DOMAIN` без `https://` и пять независимых секретов: `DJANGO_SECRET_KEY`, `DB_OWNER_PASSWORD`, `APP_DB_PASSWORD`, `MIGRATE_DB_PASSWORD`, `BACKUP_DB_PASSWORD`. Для каждого используйте случайное значение не менее 32 байт, например из менеджера паролей. Не отправляйте их в чат и не добавляйте `.env` в Git.

`FILM_DEV` и `FILM_TEST` на рабочем сервере не задавать. Compose их не передаёт. Django в production откажется запускаться без длинного секретного ключа, HTTPS-origin и PostgreSQL.

## 2. Вход по почте и Яндекс ID

Для email укажите `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`. По умолчанию STARTTLS/587; для TLS/465 выставьте `SMTP_SSL=1`. Настройте SPF/DKIM/DMARC по инструкции своего почтового провайдера, проверьте доставку реальному адресату. Коды не выводятся в консоль даже в локальном DEV-режиме.

Для Яндекса зарегистрируйте веб-приложение в Яндекс OAuth:

- callback: `https://ВАШ-ДОМЕН/api/auth/yandex/callback`;
- необходимое право: `login:info`; доступ к почте, контактам и телефону не нужен;
- `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` задаются только в `.env`;
- используется Authorization Code + PKCE, вход и привязка — через интерфейс аккаунта.

Если провайдер не настроен, его кнопка не показывается. Для автопоиска фильмов задайте новый `KINOPOISK_API_KEY`; старый ключ из истории репозитория отзовите в кабинете провайдера.

## 3. Первый запуск

```sh
docker compose config --quiet
docker compose build app migrate backup
docker compose up -d db
docker compose --profile tools run --rm migrate
docker compose up -d app caddy
docker compose exec app python manage.py check --deploy
```

Caddy получит сертификат для указанного домена. В базовой конфигурации HSTS не распространяется на поддомены и не включён в preload; предупреждения Django об этих двух опциях ожидаемы. Остальные замечания нужно разобрать до открытия регистрации.

База создаёт отдельные роли: `film_owner`, `film_migrator`, `film_app`, `film_backup`. Приложение получает только DML-права, мигратор — DDL в своей схеме, backup — чтение. Инициализация ролей выполняется только при первом создании тома PostgreSQL. Изменение пароля в `.env` не меняет пароль уже созданной роли: сначала согласованно измените его в PostgreSQL, затем пересоздайте соответствующие контейнеры.

На одном VPS app↔db используют закрытую Docker-сеть. При выносе БД в управляемый сервис замените параметры `PGHOST`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE=verify-full`, установите доверенный CA, ограничьте подключения приватной сетью/allowlist. Не отключайте проверку сертификата ради подключения.

Включите у хостинга шифрование рабочего диска и снимков, где доступно. Docker volume сам по себе не шифрует БД.

## 4. Зашифрованные резервные копии

На отдельной доверенной машине с `age`:

```sh
age-keygen -o film-backup.agekey
age-keygen -y film-backup.agekey
```

Приватный файл `film-backup.agekey` сохраните отдельно от VPS минимум в двух защищённых местах. В `AGE_RECIPIENT` на VPS внесите только публичный получатель `age1...`. Потеря приватного ключа делает копии невосстановимыми.

Создайте каталог `BACKUP_PATH`, доступный пользователю `postgres` внутри backup-контейнера. Узнайте числовые UID/GID именно своей сборки:

```sh
docker compose --profile tools run --rm --no-deps --entrypoint id backup
```

Назначьте каталогу соответствующего владельца и права `700`; не используйте `chmod 777`.

```sh
docker compose --profile tools run --rm backup
sudo cp deploy/film-backup.service deploy/film-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now film-backup.timer
sudo systemctl start film-backup.service
sudo systemctl status film-backup.service
```

Скрипт выполняет `pg_dump | age`, сохраняет только завершённую копию и checksum, удаляет свои копии старше 30 суток. Таймер — раз в сутки в 03:00 UTC. Возможна потеря изменений после последнего успешного backup.

**Каталог на том же VPS недостаточен:** настройте копирование зашифрованных файлов и checksum на отдельное приватное хранилище в РФ. Добавьте команду копирования в service; её ошибка должна завершать job с ошибкой. Включите внешнее оповещение о сбое и об отсутствии свежей копии. Провайдер хранилища и канал уведомлений не выбраны, поэтому они не выдуманы и не настроены автоматически.

## 5. Проверка восстановления

Восстанавливайте сначала в новую изолированную БД. Оригинальная рабочая БД не должна быть целью пробного восстановления.

```sh
sha256sum -c film-YYYYMMDDTHHMMSSZ.dump.age.sha256
set -o pipefail
age -d -i /защищённый/путь/film-backup.agekey film-YYYYMMDDTHHMMSSZ.dump.age \
  | pg_restore --exit-on-error --no-owner --no-acl --dbname=film_restore_test
```

Команды выполняются в Bash на доверенной машине; задайте PGHOST/PGUSER/PGPASSWORD/PGSSLMODE для изолированной БД безопасным способом. Создайте её заранее, например через `createdb film_restore_test`. Версия `pg_restore` должна соответствовать версии `pg_dump` или быть совместимой. При отсутствии pgcrypto/других расширений текущая схема их не требует.

Направьте тестовый экземпляр приложения на восстановленную БД, проверьте вход, количество просмотров/цитат, экспорт и связи. Для восстановления рабочей среды повторно примените права runtime/backup-ролей и удаления аккаунтов, выполненные после даты копии. Замените секрет сессий, чтобы не оживить старые сессии. Удалите истёкшие коды командой `prune_auth`; до открытия доступа удалите все старые EmailChallenge/Session, если восстановление было после инцидента.

`tests/backup-smoke.sh` автоматизирует проверку только на одноразовых CI-базах с именем `film_ci`; на рабочую базу его направлять нельзя.

## 6. Обновления и проверка сайта

Сначала сделайте копию и проверьте обновление на отдельной среде. Для несовместимых миграций используйте окно обслуживания.

```sh
git pull --ff-only
docker compose build app migrate backup
docker compose --profile tools run --rm migrate
docker compose up -d app caddy
docker compose exec app python manage.py check --deploy
```

Проверьте через HTTPS: вход по реальному письму, вход через Яндекс, приватность двух аккаунтов, перенос гостевых данных, конфликт двух устройств, выход из всех сессий. Перейдя с другого домена, экспортируйте гостевой архив на старом адресе и импортируйте на новом — localStorage между доменами не переносится.

В этой версии нет веб-админки. Технические операции выполняются через ограниченный доступ к серверу; не публикуйте Django admin без отдельной MFA-защиты.
